ROUND 3 — CORRECTION: THE CONTACT GATE WASN'T SENDING
========================================================

WHAT WAS WRONG IN THE ROUND 2 ZIP
--------------------------------------------------------
rpSubmitContactGate() called rpSendEstimateToGoHighLevel(), which is a
NO-OP STUB — it sets two flags and returns without sending anything:

    function rpSendEstimateToGoHighLevel(extra = {}) {
      /* Calendar-only confirmation gate: ... */
      rpState.estimateSent = true;
      rpState.preBookingWebhookSent = true;
      return true;
    }

So the gate captured a name and phone into rpState and they never left
the browser. The gate was decorative. Fixed below.

This also answers "where do unfinished bookings go?" — before this
round, NOWHERE. /book is the only endpoint the site called, and it
hard-requires a valid appointment startTime (400s without one). Anyone
who didn't reach the calendar and pick a slot vanished with no contact,
no note, no tag.

ROUND 5 — BACK BUTTON
========================================================
REPORTED: "can't hit back after selecting move-in/move-out"

DIAGNOSIS: the screenshot showed "STEP 2 OF 10". This build reports
"STEP 2 OF 11" — the contact gate adds one step. So the site being
tested was the LIVE, un-deployed build, not this one. Back button and
native browser back both verified working in this build at that exact
step and window size.

FIXED ANYWAY — a real bug found while investigating:
book/index.html, session-resume history rebuild read the raw flow table
instead of the computed flow:

  BEFORE: const flow = rpResumedSession ? (rpFlows[rpState.service] || []) : [];
  AFTER:  const flow = rpResumedSession ? rpCurrentFlow() : [];

rpFlows is the raw table and does NOT contain the injected "contactgate"
step; only rpCurrentFlow() does. On a resumed session (refresh, or
returning to a half-finished estimate within 3 hours) this rebuilt one
history entry too few, so back landed on the wrong screen. Introduced in
round 2 with the contact gate.
